## 二、读 course-rag 的框架思路（今天最大的收获）

完整专题：[35-RAG项目架构思路](../topics/35-RAG项目架构思路.md)

### 印象最深的 4 个点

**① 整个架构由"一个矛盾"决定**

```
向量化 500 块 = 10 秒（慢）
一次检索     = 0.3 秒（快）
→ 慢的离线做一次，快的在线每次做
```

**6 个文件的划分全部从这一刀派生。** 先想清楚"什么慢、什么快"，架构就出来了。

**② 每层有"绝不做"的事**

`qa.py` 知道 `store.search()` 返回 `Hit`，但**不知道笔记存在哪个文件夹**。

> **每层只知道自己下一层的数据结构。这条规则一破，项目就开始烂。**

**③ 数据契约逐层只加一个字段**

```
Doc(name, text) → Chunk(text, source) → Hit(text, source, score) → Answer(text, hits, refused)
```

好处：换任何一层，其他层不用动。

**④ 每个决策都有代价，好项目会主动写出代价**

| 决策 | 收益 | 代价 |
| --- | --- | --- |
| 自己写 splitter | 零依赖 | 不认 Markdown 结构 |
| 块前加《标题》 | 检索准 | token 变多 |
| 存 npz | 简单 | **不能增量更新** |
| numpy 手写检索 | 看得懂 | **线性扫描，10 万块会慢** |
| 阈值拒答 | 防幻觉 | **会误拒** |

`store.py` 开头自己写了"生产环境通常换成 Chroma/FAISS"。**主动承认局限**——这是好项目的标志。

### 分层的价值用数字看

| 想加什么 | 要动几个现有文件 |
| --- | --- |
| 换 embedding / 加 rerank / 换向量库 / 加流式 | **1 个** |
| **加 HTTP 接口 / 加评估** | **0 个**（新建文件即可） |
