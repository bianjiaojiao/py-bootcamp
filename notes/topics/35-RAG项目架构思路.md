# RAG 项目架构思路（以 course-rag 为例）

> 看一个真实项目的**设计思路**，不是代码清单。
> 这套框架跟"数据是什么"无关——换成公司文档/法律条文/客服话术，架构不用改。

---

## 一、起点：一个矛盾决定整个架构

```
500 个块做向量化 → 约 10 秒（慢）
一次检索        → 约 0.3 秒（快）
```

**如果每次提问都重新向量化，用户要等 10 秒。**

所以第一刀砍在这里：

| 分类 | 处理 |
| --- | --- |
| 慢的、只做一次的（向量化） | **离线**，产出 `index.npz` |
| 快的、每次都要做的（检索） | **在线**，读 `index.npz` |

**6 个文件的划分，全部从这一刀派生。**

---

## 二、五层结构，每层有"绝不做"的事

```
                    ┌─────────────────┐
                    │  入口层          │  build_index.py / ask.py
                    │  只做参数 + 打印  │  （不写业务逻辑）
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │  应用层          │  qa.py
                    │  检索+提示词+拒答 │  （不读文件）
                    └────────┬────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
    ┌─────────▼─────────┐         ┌─────────▼─────────┐
    │  存储层            │         │  切分层            │ splitter.py
    │  store.py          │         │  文本 → 块         │ （不知道文件/向量）
    │  块↔向量↔检索      │         └───────────────────┘
    │  （不调 LLM）      │
    └─────────┬─────────┘
              │
    ┌─────────▼─────────┐         ┌───────────────────┐
    │  读取层            │         │  配置层            │ config.py
    │  loader.py         │         │  路径 + 模型对象    │ （不知道业务）
    │  文件 → Doc        │         └───────────────────┘
    │  （不切块）        │
    └───────────────────┘
```

| 层 | 文件 | 只做 | **绝不做** |
| --- | --- | --- | --- |
| 配置 | `config.py` | 路径、模型对象 | 业务逻辑 |
| 读取 | `loader.py` | 文件 → `Doc` | 切块、向量化 |
| 切分 | `splitter.py` | 文本 → 块 | 知道文件存在、知道向量 |
| 存储 | `store.py` | 块 ↔ 向量 ↔ 检索 | 调用 LLM |
| 应用 | `qa.py` | 检索 + 提示词 + 拒答 | 读文件、切块 |
| 入口 | `build_index.py` / `ask.py` | 解析参数、打印 | 任何核心逻辑 |

### 核心规则

> **每层只知道自己下一层的数据结构。**

`qa.py` 知道 `store.search()` 返回 `Hit`，但**不知道**笔记存在哪个文件夹。

**这条规则一破，项目就开始烂。**

## 三、数据契约：四层数据，逐层只加一个字段

```
Doc(name, text)                ← 一篇笔记：叫什么、内容是什么
   ↓ 切块（splitter）
Chunk(text, source)            ← 一个块：内容是什么、来自哪篇
   ↓ 建索引（转成向量）
   ↓ 检索（算相似度）
Hit(text, source, score)       ← 一条结果：多了"有多像"
   ↓ 组答案（调 LLM）
Answer(text, hits, refused)    ← 一次问答：多了"是不是拒答"
```

### 为什么这样设计

| 好处 | 具体 |
| --- | --- |
| **可替换** | 换切块算法 → `Doc`/`Chunk` 契约不变，其他文件不用动 |
| **可测试** | 每层能单独测（给 `Chunk` 列表就能测 `store`） |
| **可读** | 看 `Hit` 就知道"检索结果长什么样"，不用读 `store.py` |

### `Answer` 的两个白送属性（好设计的细节）

```python
# qa.py
@dataclass
class Answer:
    text: str
    hits: list
    refused: bool

    @property
    def best_score(self):
        return self.hits[0].score if self.hits else 0.0

    @property
    def sources(self):
        """去重后的来源文件列表"""
        seen = []
        for h in self.hits:
            if h.source not in seen:
                seen.append(h.source)
        return seen
```

**调用方要"来源列表"，不用自己从 `hits` 循环提取。**
"对外像数据，对内是计算" —— 这就是 `@property` 的典型用法。

## 四、六个关键决策 + 各自的代价（最该学的部分）

> **任何设计都有代价。好项目会主动写出代价。**

### 决策 1：自己写 splitter，不用 LangChain 的

| 收益 | 代价 |
| --- | --- |
| 零依赖、每步看得见 | **不认 Markdown 结构**（标题/代码块被当普通文字） |

### 决策 2：每个块前面拼上《标题》

```python
# store.py:56
self.chunks.append(Chunk(text=f"《{title}》\n{piece}", source=doc.name))
```

| 收益 | 代价 |
| --- | --- |
| 块自带主题标签，**检索命中率明显提升** | 每块多 10~20 字，token 变多 |

### 决策 3：索引存成 `index.npz`

| 收益 | 代价 |
| --- | --- |
| 一个文件搞定，压缩后 1 MB | **不能增量更新**（加一篇笔记要全量重建） |

### 决策 4：numpy 手写余弦检索

| 收益 | 代价 |
| --- | --- |
| 零依赖、看得懂 | **线性扫描**：501 块 0.7 ms 没问题，10 万块 140 ms |

> `store.py` 开头主动写了：
> **"生产环境通常换成 Chroma / FAISS / Qdrant（它们会做索引加速）"**
> —— **好项目会主动声明自己的局限**。

### 决策 5：阈值拒答（`min_score=0.45`）

| 收益 | 代价 |
| --- | --- |
| 防止拿不相关的东西瞎编 | **会误拒**（R8 里 0.528 那个就是误判） |

### 决策 6：出处写两遍（提示词 + 代码）

```python
# ① 提示词里要求模型自己写出处（qa.py:20）
"3. 最后单独一行写：出处：文件名"

# ② 代码里再从 hits 提取 sources（qa.py:40）
@property
def sources(self): ...
```

| 收益 | 代价 |
| --- | --- |
| 双保险：模型忘了写，代码也能给出处 | 有点冗余 |

## 五、扩展点：想加功能该改哪（分层的好处全在这）

| 你想加什么 | 只改哪里 | 要动几个现有文件 |
| --- | --- | --- |
| 换更强的 embedding | `store.py` 的 `DEFAULT_MODEL` | **1 个** |
| 加 rerank（重排序） | `store.search()` 返回前插一层 | **1 个** |
| 换成 Chroma 向量库 | 只改 `store.py` 的 `search/save/load` | **1 个** |
| 加流式输出 | `qa.py` 把 `chain.invoke` 换成 `.stream` | **1 个** |
| 加 HTTP 接口 | **新建** `serve.py` | **0 个** |
| 加评估 | **新建** `eval.py` | **0 个** |
| 增量加笔记 | `store.py` 的 `save/load` 要改结构 | 1 个（但要改设计） |

**最后两行是重点：加接口、加评估，一个现有文件都不用改。**
**这就是分层的全部价值。**

## 六、一句话总结这套框架

> **离线：把笔记变成"可检索的数字"。**
> **在线：把问题变成数字，从里面找最像的几块，拼给模型让它照着答；不够像就说不知道。**

### 这套思路是通用的

换成公司文档 / 法律条文 / 客服话术 / 医学指南：

**架构一个字都不用改，只换 `NOTES_DIR` 和切块参数。**

**这就是为什么 RAG 是"通用技能"，不是"笔记问答专用"。**

---

## 七、如果从零设计，顺序应该是

```
1. 先想清楚：数据多大？一次向量化多久？（决定离线/在线怎么分）
2. 定数据契约：Doc / Chunk / Hit / Answer 各有什么字段
3. 从下往上写：config → loader → splitter → store → qa → 入口
4. 每写完一层就单独跑一次（不要全写完再跑）
5. 最后加：评估 → 接口 → 文档
```

**第 4 步是关键**——course-rag 每个文件都能 `python xxx.py` 单独跑，就是按这个顺序写出来的。
